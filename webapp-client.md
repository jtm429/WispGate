# Webapp Client Specification

## Purpose

A webapp client is a UI-bearing applet authored as HTML/CSS/JavaScript and delivered through the appserve connection. It is not necessarily a typed-input program. Its primary purpose is to provide the complete visual interface for one or more personal programs.

A webapp can run in the native client's embedded WebView and communicate with other programs through the host bridge and relay. The host does not provide a prebuilt applet UI or hard-coded applet workflow.

## Turn-based interaction

The webapp owns the application state and the complete UI. The user client is a renderer and event transport:

```text
webapp -> complete response/UI -> user client
user clicks or acts
user client -> generic action -> webapp
webapp -> next complete response/UI -> user client
```

The user client assumes the current applet state remains unchanged when no response is received. It does not predict, mutate, or reconstruct applet state locally. A response can contain a complete HTML document, a complete view model rendered by the webapp, or another self-contained representation chosen by the applet format.

Nothing applet-specific is hard-coded into the user client. Applets define their own controls, labels, layout, transitions, action names, and interpretation of input data.

## Applet package

An applet package contains:

```text
manifest.json
index.html
assets/
  app.js
  app.css
  icons/
```

The manifest contains:

```json
{
  "id": "com.example.notes",
  "version": "0.1.0",
  "entry": "index.html",
  "minimum_host": "0.1",
  "capabilities": ["actions", "responses"],
  "sha256": "..."
}
```

The package is addressed by its content hash. The relay may store or forward it, but the user client verifies the hash before loading it.

## Applet startup

The host injects the bridge before the applet starts. The applet calls:

```javascript
await appserve.ready();
const me = await appserve.identity();
```

The applet then builds its own UI and subscribes to the channels it needs.

## Actions and responses

Messages are application-defined JSON or binary payloads. A user action is an event generated by the rendered UI:

```javascript
await appserve.send_action({
  type: "button_click",
  control: "refresh",
  request_id: "..."
});
```

The applet service responds with the next complete applet response. The relay sees routing metadata but not the encrypted payload.

## UI expectations

The applet should:

- render without a public network origin;
- use the bridge rather than direct arbitrary sockets;
- tolerate reconnects and duplicate events;
- display connection state where useful;
- keep application state in the applet service or in the response model;
- avoid treating a delivery acknowledgement as proof that the target processed a request.

## Optional applet lifecycle hooks

```javascript
export async function onStart(context) {}
export async function onMessage(message) {}
export async function onSuspend() {}
export async function onStop() {}
```

These are conventions for the first runtime, not requirements on the relay.

## Applet updates

A newer package is selected by ID and version, downloaded over the appserve connection, hash-checked, and then loaded. The host should retain the previous package until the new one has passed validation and startup. A bad update can therefore be rolled back locally.
